# P3.5 Async OCR UX + Background-Job Baseline — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan phase-by-phase. Each phase has checkbox (`- [ ]`) steps. Phases are sequential — do not start phase N+1 until phase N is green and committed.

**Goal:** Move OCR off the form-submit critical path. Parent uploads a document, the upload returns immediately, OCR runs in a background worker, the page polls for status, and on completion fields prefill (if empty) or surface an inline suggestion chip (if the parent already typed something). The form remains interactive throughout.

**Architecture:**
- Adopt **django-q2** with the Django ORM broker — no Redis dependency for the club-scale single-instance app. Worker process: `uv run python manage.py qcluster`.
- Split the synchronous OCR call out of `apps/registrations/services.py`. Document creation enqueues a job; the job calls the existing `safe_extract_document_data` and persists results exactly as P3 does today (no change to the encrypted-payload/summary storage contract).
- Add a small async-upload endpoint at `POST /applications/<id>/documents/` for the JS-enhanced flow. Existing synchronous form-submit path remains as the no-JS fallback (still enqueues OCR; only the front-door changes).
- Add a status endpoint at `GET /applications/<id>/documents/<doc_id>/status` returning `{ocr_status, ocr_error_code?, extracted_fields?}`. Frontend polls with backoff.
- Frontend prefill rule (per OCR field): if form input is empty/whitespace, fill and tag source as OCR; if non-empty, render an inline suggestion chip with Accept / Dismiss. Dismissals are session-only (no DB persistence in first slice).
- `Document.OcrStatus` already has `NOT_REQUESTED / PENDING / COMPLETED / FAILED`. We reuse `PENDING` for "enqueued or running" — no migration needed.

**Tech Stack:** Python 3.12, Django 5.x, **django-q2** (new), Vanilla JS + Fetch API for frontend polling (no new frontend framework), `pytest` (with `pytest-django`), `ruff`, `mypy`, `uv`.

**User-locked decisions:**
- Worker runs in a separate terminal (`uv run python manage.py qcluster`). Documented in `AGENTS.md` and `README.md` quickstart. No auto-spawn, no `sync: True` in DEBUG.
- Submit-while-OCR-pending is allowed. Submitted application captures whatever OCR completed. Matches the P3 non-blocking guarantee.
- Dismissed suggestions are session-only. No `DocumentExtractionDismissal` table.

## Phase 4: Prefill-vs-suggestion UX

**Goal:** When OCR completes, fields whose current value is empty/whitespace get auto-filled; fields whose current value is non-empty get an inline suggestion chip with Accept / Dismiss.

- [ ] **Step 4.1 (TDD)** — Unit test `tests/registrations/test_ocr_prefill_vs_suggestion.py::test_classify_field_action`:

  - Empty / whitespace + OCR value → `"prefill"`.

  - Same current and OCR value (case-insensitive trim) → `"noop"`.

## Risk Register

| Risk | Mitigation |
|---|---|
| Worker process forgets to load `OCR_ENCRYPTION_KEY` (decryption fails silently in job) | Document worker env in `AGENTS.md`; add a startup check that fails fast if key is missing |
| Polling backoff exceeds reasonable wait time on slow tiny-IDP responses (P3 saw 9.6 s max) | Cap polling window at 30 s with backoff; after that show "OCR is taking longer than usual — you can submit now and we'll continue in the background" |
| User submits, OCR completes later, but admin review expects prefilled fields | Job skips `field_sources` mutation when `application.status != 'draft'`; admin sees the `DocumentExtraction` row regardless |
| JS dispatched `change` event triggers form-level dirty-tracking, marks the draft as dirty even though OCR did the fill | Ensure draft-dirty detection is value-based, not event-based, OR explicitly suppress the OCR-origin events |
| django-q2 job loses task on process kill mid-extraction | `max_attempts=2` covers one redelivery; document a manual recovery: admin re-OCR if PENDING for >5 min |
| Suggestion chip and prefill badge add visual noise on a busy form | Visual design review during Phase 4; chip should be subtle (small, gray, single-line) |
| Stub-mode tests no longer exercise the synchronous path that older tests assumed | Phase 1 Step 1.9 converts those tests to use django-q2 `sync=True` |
