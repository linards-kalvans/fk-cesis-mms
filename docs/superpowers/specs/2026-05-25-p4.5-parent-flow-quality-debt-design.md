## Background

Six pre-existing bugs surfaced during the Slice E manual LAN check (2026-05-25). One (the redundant "Saglabāt melnrakstu" button on the review step) was fixed immediately in the Slice E follow-up commits. The remaining five are addressed here.

Items are grouped into two independent slices:

- **Slice 1 (data layer):** items 2 + 3 — pure Python, no JS, verifiable with tests alone
- **Slice 2 (display + wizard UX):** items 1, 4, 5 — client-side DOM and wizard behaviour, verified by LAN device check

## Slice 1 — data layer

### Item 2a: Guardian full-name doubling on new-app prefill

**File:** `apps/registrations/services.py` — `_merge_ocr_extractions`

**Root cause.** When building the OCR-priority prefill for a new application, the code constructs the guardian name as:

```python
existing = result.get("guardian_full_name") or str(latest.guardian_full_name ...)
result["guardian_full_name"] = f"{existing} {full_name}".strip() if existing else full_name
```

`existing` falls back to the model value already placed in `prefill` by the caller (`get_application_prefill`, lines 115–121). When OCR also returns the same name the result is `"Anna Bērziņa Anna Bērziņa"`.

**Fix.** Drop the fallback; OCR wins unconditionally:

```python
result["guardian_full_name"] = full_name
```

Same pattern applies to `guardian_personal_id` (confirm there is no equivalent fallback bug there — the current code just sets it directly, which is fine).

---

### Item 2b: Member fields bleeding into new-app prefill

**File:** `apps/registrations/services.py` — `_merge_ocr_extractions`

**Root cause.** `_merge_ocr_extractions` builds `member_full_name` and `member_personal_id` from prior-application OCR extractions. But `get_application_prefill`'s own docstring states: "Member/child fields are NOT prefilled — the user enters a new child each time." Member OCR was incorrectly included in the function.

**Fix.** Delete the member OCR extraction block (the `if not member_merged:` loop body, currently lines 165–189). The function is only called for new-app prefill. Member OCR suggestion in the existing-application workspace is handled live by `async_upload.js` polling `_ocr_extracted_fields` — that path is unaffected.

### Item 3: OCR stub missing `date_of_birth`; DOB not wired into workspace prefill

**Part A — Stub (`apps/integrations/ocr.py`, `_stub_extraction`)**

Add `date_of_birth` to `person_fields` in the stub response so it matches the canonical schema the live tiny-IDP extractor produces:

- `member_identity` → `"date_of_birth": "2015-06-15"` (plausible child DOB)
- `guardian_identity` → `"date_of_birth": "1985-03-10"`

No changes to `document_metadata`, `confidence`, or `raw_reference`.

**Part B — OCR field mapping (`apps/registrations/views.py`, `_ocr_extracted_fields`)**

Currently the function maps `first_name + last_name → <role>_full_name` and `personal_id → <role>_personal_id`. It does not map `date_of_birth`.

For `MEMBER_IDENTITY`, also extract `date_of_birth` from `person_fields` and map it to the form field `member_birth_date`. This is the Django form field already declared in `apps/registrations/forms.py` (line 64).

Resulting addition to the function body (member branch):
```python
dob = str(person_fields.get("date_of_birth", "")).strip()
if dob:
    fields["member_birth_date"] = dob
```

No model or migration changes required.

## Slice 2 — display + wizard UX

### Item 1: Document card not reflecting upload state after async upload

**File:** `static/js/async_upload.js`

**Root cause.** The document card (header badge + body text) is static server-rendered HTML. After a successful async upload POST, `async_upload.js` only updates the progress slot and starts OCR polling — it never touches the card DOM. The card continues to show "Nav augšupielādēts" even after a successful upload.

**Fix.** Immediately after a successful upload POST response (before OCR polling starts), update the card DOM in `bindFileInput`:

1. Locate the `.fk-document-card` ancestor of the file input.
2. Header badge: remove the `fk-source-badge--inactive` element, insert `<span class="fk-source-badge fk-source-badge--active">Aktīvs</span>`.
3. Body: replace the "Dokuments nav augšupielādēts." paragraph with:
   - `<p class="fk-document-card__filename">{filename}</p>` (using `input.files[0].name`)
   - `<p class="fk-document-card__hint">Dokuments jau ir augšupielādēts.</p>`
4. Inside `.fk-upload-slot` (the direct parent of the file input), insert `<span data-uploaded-document hidden></span>`.

Step 4 is the DOM hook that item 5 relies on (see below). No server-side change needed; the filename is available from `input.files[0].name`.

### Item 5: Step-gating doesn't recognise pre-filled values on `edit`/`fix_requested` resume

**Files:** `templates/parent_ui/includes/document_card.html`, `static/js/wizard.js`

**Root cause.** `wizard.js::isFileFieldFilled` runs on page load to decide whether the "Turpināt →" button should be enabled. It checks three things for file inputs:

1. `input.files.length > 0` — always 0 on a page reload (no file selected in the current session).
2. `.fk-dropzone--filled` class on the nearest `.fk-dropzone` — the document card does not use `.fk-dropzone`; the input lives inside `.fk-upload-slot`.
3. `[data-uploaded-document]` inside the nearest `.fk-form-field` — the input is inside `.fk-upload-slot`, not `.fk-form-field`, so the query finds nothing.

All three checks fail → file considered empty → step 1 gate stays disabled even when documents are already uploaded.

**Fix — two parts:**

**Part A — `document_card.html`.** Inside the `{% if document %}` branch (document already uploaded at page load), emit the DOM hook inside `.fk-upload-slot`:

```html
<span data-uploaded-document hidden></span>
```

This is the same marker item 1's JS writes after a fresh async upload, so both paths (page-load resume and fresh upload) share one signal.

**Part B — `wizard.js::isFileFieldFilled`.** Add a fourth fallback after the existing three checks:

```js
var slot = input.closest('.fk-upload-slot');
if (slot && slot.querySelector('[data-uploaded-document]')) return true;
```

The combined result: on resume, the server-rendered marker fires; after fresh upload, the JS-inserted marker fires; `isFileFieldFilled` returns `true` in both cases and the step gate enables correctly.

### Item 4: Mobile users cannot forward-jump to previously-visited steps

**Files:** `static/js/wizard.js`, `static/css/parent_theme.css`

**Root cause — two issues:**

1. No concept of "visited" steps exists. The stepper click handler calls `showStep(i)` for any indicator click, including forward jumps to unvisited steps that would bypass step gating.
2. `.fk-step-number` circles are `38 × 38 px`, below the 44 px minimum touch target required by P4 acceptance criteria, making taps unreliable on narrow viewports.

**Fix — three parts:**

**Part A — visited-step tracking (`wizard.js`).** Introduce a `visitedSteps` Set. Initialize it with `startStep`. `showStep(n)` adds `n` to the set at entry. Stepper click handler: call `showStep(i)` only if `visitedSteps.has(i)`.

```js
var visitedSteps = new Set([startStep]);

// inside showStep(n):
visitedSteps.add(n);

// inside indicators click handler:
indicator.addEventListener('click', function () {
  if (visitedSteps.has(i)) showStep(i);
});
```

**Part B — visual affordance (`wizard.js` + `parent_theme.css`).** Inside `showStep(n)`, after `visitedSteps.add(n)`, sync indicator classes: add `fk-step--visited` to all indicators whose index is in `visitedSteps`, remove it from all others. CSS rule: `fk-step--visited` gets a slightly stronger text colour than muted (e.g. `var(--fk-dark)`) with `cursor: pointer` reinforced, so the user can visually distinguish navigable from locked steps.

**Part C — touch target (`parent_theme.css`).** Increase `.fk-step-number` to `44 × 44 px` (from `38 × 38 px`) so taps are reliable on mobile. Update `top` on the connector pseudo-element (`::before`) from `18px` to `21px` to keep the horizontal connector centred.
